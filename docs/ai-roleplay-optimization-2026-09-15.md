# AI 酒馆实现对照与剧本杀项目优化建议

调研日期：2026-09-15。工作空间基线：`d7d75d28699f64d3d848d6eb066cd780dce62398`。本文结合本地源码和官方资料，给出实现建议；不是已经完成的功能声明。热门项目的关注度、固定版本源码与机制细节见配套的[外部项目调研](research/2026-09-ai-roleplay-projects.md)。

## 1. 结论与适用边界

当前项目已经具备 AI 酒馆常见的滚动摘要、向量检索、人设提示、点名响应、私聊和生成后检查。下一步最有价值的是补足这些机制的正确性和可观察性：**让 AI 知道什么可以说、何时可以说、说法来自哪里，并控制每次调用所使用的信息和预算。**

首批建议：补齐条件秘密的提示、增加公开证据的可靠保留、隔离不同 embedding 模型、建立输入上下文预算。随后改善角色决策、发言归属和评估。

酒馆通常允许用户自由改写历史、重说和探索分支；本项目是真人参与的多人推理游戏，线索、投票与行动点具有共同状态。因此可以借鉴酒馆的上下文工程和记忆失效规则，但不能直接移植全角色卡合并、自由改写已提交历史、无限自主插话、把用户世界书提升为系统指令等做法。

## 4. 优先级与实施范围

工作量 S/M/L 是相对规模，不是交付日期。P0 表示建议下一批先做，不表示已测得生产故障。

| 优先级 | 建议 | 主要解决的问题 | 规模 |
| --- | --- | --- | --- |
| P0 | 完整传入秘密披露规则 | 条件秘密长期不交代，角色目标与行动脱节 | S |
| P0 | 公开证据登记与来源保留 | 摘要后遗忘证据细节，把玩家陈述当事实 | M |
| P0 | embedding 模型与版本隔离 | 换模型后检索使用不兼容向量 | S–M |
| P0 | 输入预算与 prompt 诊断 | 长局上下文失控，无法解释裁剪和漏信息 | M |
| P1 | 模型能力与参数优先级 | 系统消息降格、温度配置无效、协议差异被掩盖 | M |
| P1 | 结构化行动计划与角色样例 | 所有角色表现得相似，回避问题、重复提问 | M |
| P1 | generation ID 与端到端取消 | 同座位流混入、迟到输出和过期状态污染 | M |
| P1 | 对局质量评估集 | 流程测试通过，但无法判断扮演是否改善 | M |
| P2 | 作者试演与受控备选回复 | 剧本制作和人工纠偏体验 | M–L |

### 4.1 条件秘密：先使已有数据生效

**已确认事实：**`schema.ts:78` 定义 `never / conditional / must_share`，并要求 conditional 有 condition。但 `context.ts:131–133` 渲染秘密时，只对 must_share 加标记，conditional 的条件没有输出；其余秘密共用“绝不能主动告诉任何人”的描述。`guard.ts:37–43` 也只匹配 never 的部分原文。

本地 34 本正式种子、188 个角色共有 128 个 never 秘密和 60 个 conditional 秘密。对《雪乡夜话》的角色注入唯一条件标记并调用真实 `buildPlayerContext`，确认标记不在生成的上下文里。

**建议实现：**每个秘密明确展示披露模式与条件。never 是不可披露；conditional 在满足条件时允许披露；must_share 需要在合适时机主动说出。动态的“条件已满足”提示放在 user 尾部，保持同座位的 system 稳定。

第一步可以只完整渲染自然语言 condition，减少风险。需要稳定判定的条件再增加类型化触发，如指定线索已公开、进入某幕、被指定问题质询；保留自然语言描述作为解释，避免把所有条件做成脆弱关键词匹配。

**验收：**未满足条件时不鼓励泄露；满足条件时能解释允许透露哪部分；must_share 不再全程藏牌。提示构建测试验证字段传递，独立对局样例验证实际披露行为。不得因此向 AI 注入他人的条件秘密。

### 4.2 公开证据应有独立的保留机制

**已确认事实：**`context.ts:99–100,147–150` 的线索块只渲染自己持有的卡，公开线索靠事件记录进入其他座位的上下文。公共记录摘要后，卡的细节可能仅剩概要。`engine.ts:175–179` 只索引公共 speech；`recall.ts:52–54` 候选也只接受 speech，不能召回 clue 事件。

因此某张关键物证即使已经全场公开，摘要丢掉精确时间/数量后，也没有可靠途径从检索恢复卡片原文。用人工构造的有损摘要替换 clue 事件，真实 context builder 在摘要前包含证据标记、摘要后不包含。这个实验确认的是信息路径缺口，**没有测量实际 LLM 的摘要丢失率**。

**建议实现：**增加从 `state.clueStates.isPublic` 派生的公开证据登记。它与持有线索分开，先保留公开证据 ID、要点与可回查的原文；关键证据是否常驻应由玩家可见信息和任务相关性决定，不能用 `truth.keyEvidenceIds` 偷渡上帝视角。

每条派生记录携带 `sourceSeqs / clueIds / visibility / kind`。玩家声称“九点人在书房”只能记录为“某玩家声称九点人在书房”；看到物证与推断身份分别标注。矛盾保留两种说法及各自来源，不能由摘要员自行裁定其中一种是真相。

检索扩展到公开 clue 与必要的 phase 信息，再以线索 ID、人物、时间点的精确匹配补充向量检索。命中后恢复完整事件或卡片相关段落，不宜固定截前 140 字而丢失后半句的否定或时间。

**验收：**摘要后仍能回答已公开卡的时间、数量和地点；同一矛盾的双方陈述均可追溯；任何证据在注入前仍经过可见性检查。不要一开始引入大型知识图谱或向量数据库。

### 4.3 向量模型隔离和失效协议

**已确认事实：**`EventVector` 只有 gameId、seq、vector，没有模型、provider、维度或内容 hash。`recall.ts:28` 按两个向量长度的最小值计算余弦，没有拒绝维度不一致。同维不同模型的空间也不能认为兼容。

**建议实现：**缓存键绑定 embedding 空间标识、模型版本、维度、源文本 hash。默认把 provider/base URL 的非敏感指纹和 modelId 纳入空间标识；如果不同端点明确提供相同空间，可显式配置共享，不能猜测。不要在日志中暴露 API Key。

绑定变化后旧空间停止参与召回，后台重建当前空间；过渡期依靠原文窗口、证据登记与摘要。维度不一致、非有限数值、异常向量立即拒绝。失败队列要有可重试或补建途径，当前 queueEmbed 调用失败会丢弃批次，不能默认索引总是完整。

**检索输入也必须投影：**`agents/index.ts` 的 recallFor 先 `slice(-4)` 再筛 speech，不带当前问题，也未先调用 visibleTo。正常私聊类型是 private，不会直接成为该 query，因此不能据此断言现有私聊已泄露；但未来有隐藏 speech 时存在路径风险。应先筛座位可见事件，再取最近相关发言，并加入当前任务/质询/目标线索作为查询。

### 4.4 输入预算：不能只限制输出 token

**已确认事实：**`ModelBinding.maxTokens`、`output-tokens.ts` 都明确是输出上限；当前没有模型输入窗口和分块预算。`RECENT_WINDOW_CHARS=6000` 只控制摘要切分，不控制整份角色卡、线索、私聊和阶段知识。没有有效记忆时 context 退回全量记录。

用 200 条合成公开发言、无摘要构建上下文，输出为 51,542 字符；此处**字符不等于 token**，实验只确认 builder 未限制输入长度。现有真实对局的输入 token 分布尚未统计。

**建议实现：**在模型绑定增加 `contextWindow`，在模型适配层计算：可用输入 = 上下文窗口 − 输出预留 − 协议/模板安全余量。按后端 tokenizer 计数；无法获得时采用保守估算，并说明估算误差。

context 内部先形成有标签的块：角色规则、当前任务/问题、公开证据、本人持卡、已解锁知识、矛盾摘要、相关召回、近期发言、旧闲聊。只在投影后的内容上排序和分配预算。优先保留当前待答问题、规则、必要证据；旧闲聊和低相关召回先裁。

固定块已经超过模型窗口时应明确失败或切到兼容的大窗口模型，不能静默截掉红线或把当前问题挤掉；fallback 改变窗口时要重新检查预算。固定角色前缀在开局/模型配置版本上编译，局内动态提示放尾部，兼顾缓存稳定。

**可观察性：**为一次生成记录 requestId、模型、上下文各块 token、入选事件 ID、摘要锚点、召回分数、裁剪原因。开发者可以看自己的座位投影；完整诊断只对授权作者/管理员开放，不能把其他人的私卡展示给普通玩家。

### 4.5 模型能力和参数配置

**已确认事实：**`client.ts:127–138` 的 toCompatibleMessages 对所有调用移除 system 并合并到第一条 user；callOnce 与 chatStream 都调用它，也包括 Anthropic。稳定文本前缀仍在，但协议上的 system 优先级没有保留。函数注释说用于“部分网关”，实际是普遍处理。

`client.ts:155,255` 用 `opts.temperature ?? b.temperature`；agent 方法大多显式指定 temperature，所以设置页的绑定温度在这些任务里不生效。另一个参数 maxOutputTokens 则是绑定值优先，行为不统一。`jsonMode` 有类型但没有实际启用结构化输出。

**建议实现：**为接入方明确标注 system、结构化输出、采样、思考开关、tokenizer、上下文窗口等能力。支持 system 的协议保留 system，仅不支持的网关启用兼容合并。不要默认所有后端理解同一种 thinking 扩展字段。

参数合成要区分后端硬限制、用户配置和任务默认值，并在诊断里显示最终值与来源。发言保持开放文本；搜证、公开选择、投票、答题采用能力允许的结构化输出，并在本地再次 schema/候选校验。审查和压缩可独立记录 taskType，避免现在均混在 player/culprit 用途中而难以拆分成本。

### 4.6 角色扮演应由处境驱动

**已确认事实：**persona 包含 habits/taboos，但 `context.ts:137` 只用 speechStyle 与 traits；私密 relationships 也未直接渲染。当前正式种子未填写 habits/taboos/private relationships，所以它们是可扩展能力缺口，不能认为已经影响了所有存量剧本。唯一标记实验确认这两个 persona 字段不会进入 prompt。

角色的系统策略主要按凶手/无辜者二分，目标标题虽注入，却缺少持久的“当前打算达成什么”。复读检测只比较上一段开头 8 个有效字符，改个开头就可能漏检。

**建议实现：**先完整利用已有 persona 和本人关系，再由作者提供少量场景对话样例：被质询时如何回应、是否愿意交代某事实、怎样交换情报。样例展示口吻和行为，避免写出未来未解锁内容；不要直接照抄酒馆角色卡中的任意 system 覆盖字段。

为一轮行动增加小型、schema 约束的计划：当前目标、回应对象、依据的可见信息 ID、想公开/保留哪些已知事实、一个可执行动作。它是角色私有决策状态，不向全场广播，也不要求生成长篇思维链。

对搜证、发言、提问、私聊共享这一目标，避免各调用互不记得自己刚刚的意图。先在凶手和被强制质询的座位试验，使用阶段/任务版本控制过期计划；不要每条公共消息后让所有 AI 都额外思考一次。

### 4.7 流式输出要有明确归属和取消

**已确认事实：**当前正式回合已有 turnToken 和 stale 提交检查；但 delta 仅以 seat 识别，没有 generationId。consumeStream 超时后停止转发，本体直到 client 内独立 AbortSignal 超时才关闭；这不是引擎可控的端到端取消。同座位正式发言与插话存在流归属不明确的设计空间。

`refineSpeech` 在部分内容已经流向浏览器后才做软审查；最终落库文本替换原稿，不能抹去观众已经看到的内容。guard 是原文片段剥句，不能保证语义改写的秘密不会泄露，也会可能误伤合理公共表述。它应作为防线之一，不能作为秘密不泄露的完整证明。

**建议实现：**一次生成从准备、delta、提交/撤销都携带 generationId、座位、阶段版本和任务类型；引擎持有 AbortController，并传到模型请求。过期判断不仅保护最终提交，也要防止旧任务清除新任务的 thinking/inFlight 标志。质量审查与安全判定明确分工。

对需要语义安全保证的片段，在首次展示前检查；普通片段可以保留句级流。记录首次安全展示的延迟，与模型首 token 延迟分开衡量。具体是否增加 LLM 安全审查，应以泄露样例的漏报、误报与延迟实验决定。

**验收：**同座位并发任务的 delta 不互相覆盖；阶段切换后旧流不再展示；取消能关闭后端请求；审查修订不会被误认为另一回合。SillyTavern/Risu 的生成归属和取消机制可以作参考，但不能替代游戏状态的事务和版本检查。

### 4.8 建立针对剧本杀的评估

ThinkThrice 将角色信息掌握、推理与指凶纳入评估；PLAYER* 强调基于目标和信息价值的提问；Murder Mystery Agents 研究问题与回答的衔接。它们适合启发评估设计，但其自动对局结果不能直接证明真人混合局的体验收益。[ThinkThrice](https://aclanthology.org/2024.findings-acl.490/)、[PLAYER* v5](https://arxiv.org/abs/2404.17662v5)、[Murder Mystery Agents v2](https://arxiv.org/abs/2412.04937v2)。

建议从已有原创剧本构造五类固定快照：开场、关键卡公开后、时间线冲突、秘密条件满足前后、投票前。每个快照保存合法视角与期望约束，不把答案发给被评估玩家。

| 维度 | 测量方式 |
| --- | --- |
| 信息边界 | 未公开信息泄露次数、语义改写泄露、错误声称知道秘密 |
| 证据与记忆 | 已公开卡细节问答准确率、引用来源有效率、矛盾保留率 |
| 条件披露 | 条件前越界率、条件后合理披露率、must_share 全局遗漏率 |
| 回应质量 | 是否回应被问的具体问题、质询是否转移话题、提问是否重复 |
| 人设 | 作者盲评角色辨识度、风格与目标一致性，结合复读/OOC 计数 |
| 体验与成本 | 首次安全展示 P50/P95、每轮 token、每类任务耗时、fallback/超时/摘要更新次数 |

对同一批快照、同一模型与配置进行前后比较，并重复采样；先获得基线，再设目标。投票准确率仅是一个指标，不能以 AI 更快破案替代真人参与感。LLM 评分可辅助，信息权限与来源有效性应尽量用确定性检查，关键演绎仍需人评。

## 5. 推荐分批顺序

1. **先修提示与检索数据契约：**conditional 完整渲染、公开证据登记、向量空间隔离，添加对应回归样例。
2. **再控预算与调度：**模型能力、上下文块和诊断、generation ID/取消。保留稳定角色前缀和现有互斥提交模式。
3. **随后提升演绎：**作者场景样例、角色目标计划、问题回应与重复话题检测，通过固定快照和混合局试演验证。
4. **最后增加产品纠偏：**作者沙盒提供上下文检查和备选台词；真人局已提交的发言、线索、投票不允许单方自由回滚。正式分支功能另立项，须同时处理快照、摘要、索引、行动点和全场可见历史。

不建议当前引入：全角色私卡合并、无限自主群聊、长期跨局人物记忆、大型知识图谱、用户可运行的任意脚本、为每个发言全员规划和全量审查。它们或违反信息边界，或增加成本，尚无本地数据证明必要。

## 6. 本次验证与限制

- `npm test`：21 个测试文件、175 项测试通过。现有测试主要证明流程和部分规则，不等于扮演质量评估。
- 本地静态统计：34 本正式种子，188 个角色，60 个 conditional 秘密；统计不含 fixtures/examples。
- 真实 context builder 的只读合成实验：条件、habits、taboos 唯一标记未注入；200 条无摘要事件得到 51,542 字符提示；有损摘要后非持卡座位的公开证据原文标记丢失。
- 上述实验没有调用真实 LLM、没有改写种子/数据库，也没有测真实漏报率、检索命中率、token 节省或玩家满意度。效果改善是待验证假设。
- 本次只新增调研文档，没有修改应用代码、模型绑定、数据库或部署。
